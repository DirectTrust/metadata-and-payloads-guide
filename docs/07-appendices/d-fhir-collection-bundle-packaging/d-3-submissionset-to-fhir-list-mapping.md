# D.3 SubmissionSet to FHIR List Mapping

SubmissionSet-to-FHIR List mapping inventory.

## D.3.1 Mapping Principles and Governing Profiles

The MAP SubmissionSet profile derives directly from the FHIR R4 List. IHE MHD Minimal SubmissionSet is a compatibility reference, not the mandatory baseDefinition. One MAP List profile permits List.mode=working or List.mode=snapshot through a Required binding to MAPSubmissionSetListModeVS. The current transaction SubmissionSet uses working; when the applicable Transaction Definition calls for an identification-only original SubmissionSet snapshot, that separate List uses snapshot. The mode is consistent with FHIR List maintenance semantics and does not, by itself, universally define transaction role. MAP Chapter 3 and applicable Transaction Definitions govern conditional metadata and membership requirements.

## D.3.4 SubmissionSet Membership and Identifier Relationships

For the current transaction SubmissionSet (working), List.entry.item references each submitted information object DocumentReference. Bundle.entry alone does not establish SubmissionSet membership. For an original SubmissionSet identification snapshot (snapshot), List.entry MAY be absent and SHALL NOT be interpreted as a complete reproduction of original package membership. List.id is a FHIR logical identifier and is not a substitute for the SubmissionSet uniqueId or entryUUID metadata.

**Workflow-status interpretation. In send-workflow-status, the current transaction SubmissionSet (working) identifies the submitted report objects. A distinct original SubmissionSet identification snapshot (snapshot) is the Primary Information Object and carries the original SubmissionSet.uniqueId, purpose, sourcePatientId and intendedRecipient for correlation. The four FHIR mappings are respectively typed List.identifier, List.extension\[map-submission-purpose\].valueCodeableConcept, List.extension\[map-submissionset-sourcePatientId\], and List.extension\[ihe-intendedRecipient\]. List.subject identifies exchange-domain patientId and SHALL NOT be substituted for sourcePatientId. The applicable send-workflow-status GenTXDef governs correlation, handling of legitimately absent identifiers, and administrative anomalies.**

## D.3.5 Conformance and Mapping Constraints

MAP SubmissionSet FHIR mapping is specified by the tables above and accompanying extension definitions. The single MAP List profile permits working and snapshot; the original identification-only snapshot need not reproduce List.entry membership. Current transaction SubmissionSet membership remains mandatory under D.2. PatientId and sourcePatientId are distinct metadata elements; List.subject represents the exchange-domain patientId and List.extension\[map-submissionset-sourcePatientId\] preserves the originating source patient identifiers. Transaction-specific correlation requirements are governed by the applicable GenTXDef.
