# 3.9.7 Workflow Status Update Endpoint Accumulation

When a Task is present and workflow-status reporting is required, the transaction-initiating system SHALL identify at least one Workflow Status Update Endpoint in the Task, subject to applicable endpoint capability and routing requirements. When no Task is present, the fallback routing rule below applies. Inclusion of a Task without an applicable reporting obligation does not itself require TX8 endpoint.

Preserve existing endpoints = SHALL. When a Task is present, each subsequent Sender Actor SHALL preserve all Workflow Status Update Endpoints already associated with the originating Transaction Instance.

Add your own endpoint = MAY. When a Task is present, an Intermediary Sender Actor MAY add its own Workflow Status Update Endpoint when that intermediary also needs to be informed of the eventual structured payload acceptance or structured payload rejection outcome. The intermediary SHALL apply the representation-update rules in Sections 3.5.2 and 3.5.3: preserve the shared Workflow Activity business identifier, carry the updated Task representation with a new Task.id, and update package membership, affected references, and applicable Provenance. The additional endpoint does not create a new logical Task or Transaction Instance.

When a Task is present, the Content Creator MAY obtain the initial Workflow Status Update Endpoint from the supplied endpoint discovery information or explicit configuration. The selected endpoint SHALL be carried in the originating Workflow Activity Task. Each subsequent Sender Actor SHALL preserve the carried endpoints rather than depend on discovery to reconstruct them. When TX8 is required, Workflow Status SHALL be sent to each unique Workflow Status Update Endpoint accumulated for the originating Transaction Instance. Duplicate Direct addresses SHALL result in a single TX8 delivery to that address for the same reportable outcome.

The DirectTrust Directory SHALL be the authoritative source for discovering an endpoint's CapabilityStatement. The Endpoint CapabilityStatement SHALL be the authoritative declaration of the transactions and Technical Actor Roles supported by that endpoint. Directory attributes, including SERV_DESC, MAY provide human-readable summaries of endpoint capabilities but SHALL NOT independently establish support for a transaction. When determining whether an endpoint is eligible to receive TX8 Workflow Status Update, the sending system SHALL evaluate the endpoint's CapabilityStatement discovered through the DirectTrust Directory.
When the originating structured payload does not contain a Workflow Activity Task and TX8 Workflow Status Update is required, the receiving system SHALL use the Direct address established for Message Delivery Notifications as the sole Workflow Status Update Endpoint, provided that the address is associated with an Endpoint CapabilityStatement discoverable through the DirectTrust Directory that declares TX8 Receiver support (workflow-status reporting, supportsReceive=true). An endpoint whose CapabilityStatement does not declare TX8 Receiver support SHALL NOT be considered an eligible destination for TX8. The presence of workflow-status-update in a Directory SERV_DESC attribute SHALL NOT independently establish eligibility. No additional Workflow Status Update Endpoints SHALL be notified for that originating Transaction Instance.
When TX8 Workflow Status Update is required and no eligible Workflow Status Update Endpoint can be resolved in accordance with the applicable routing requirements, the receiving system SHALL NOT attempt to dispatch TX8 without a resolved destination. The receiving system SHALL record TX8 reporting obligation as unsuccessful, identifying the inability to resolve an eligible Workflow Status Update Endpoint as the reason for failure. The inability to dispatch TX8 SHALL NOT, by itself, alter the processing outcome of the originating Transaction Instance.
