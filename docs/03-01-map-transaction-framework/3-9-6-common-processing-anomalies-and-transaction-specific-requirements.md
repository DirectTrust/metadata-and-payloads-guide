# 3.9.6 Common Processing Anomalies and Transaction-Specific Requirements

All MAP Transactions SHALL apply the common processing anomaly handling requirements. Terminal outcome reporting through TX8 SHALL apply when required by the applicable Transaction Definition or workflow-status reporting obligation. The common anomaly categories include an unauthorized sending entity, an unsupported declared use case, a structured payload that does not meet the declared use case or endpoint capabilities, inability to resolve the patient required for processing, and inability to resolve an established Context Instance required for processing.

The common anomaly categories SHALL use the shared failure-reason terminology and Extensible binding specified in Section 3.9.2. Unknown patient identity does not automatically establish patient-not-found when the transaction permits registration or establishment of identity. Absence of an optional Context identifier does not establish context-not-found. Required patient or Context identifiers SHALL NOT be fabricated to make a failed package appear processable.

Each initiating Transaction Definition SHALL define the processing required to perform its Shared Activity successfully. Its Section 7 SHALL specify any additional transaction-specific processing rules, anomaly conditions, or qualifications beyond the common handling defined in TX8. Whether a patient or Context resolution condition prevents successful processing SHALL be determined against those transaction requirements; an absent optional Context identifier does not, by itself, establish a processing failure.

When an anomaly results in a defined processing failure requiring Workflow Status, the Information Recipient SHALL attempt reporting through TX8 according to Sections 3.9.2 and 3.9.7, subject to the declared TX8 capabilities and eligible destination requirements. If dispatch cannot occur, record the unsuccessful reporting obligation; do not change the originating transaction outcome or generate TX8 in response to TX8. A dispatched report SHALL identify the applicable failure reason and correlate to the originating Transaction Instance. Successful Direct delivery alone does not establish successful processing.

TX8 Transaction Definition provides the common anomaly handling details and relevant XD and FHIR examples of structured payload acceptance and structured payload rejection. Other Transaction Definitions SHOULD reference those examples and use their own Section 8 for examples specific to the initiating Shared Activity. A subsequent, separately performed workflow activity has its own processing outcome; failure of that later activity does not change an already established successful outcome of the originating transaction.
