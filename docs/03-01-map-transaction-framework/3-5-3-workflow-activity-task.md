# 3.5.3 Workflow Activity Task

When included, the Workflow Activity Task provides a machine-processable expression of the sender’s requested activity, subject to the receiving endpoint’s declared capabilities, applicable transaction requirements, and processing policies. It identifies the Shared Activity, associates it with applicable Context Instance(s), carries transaction correlation when required, and conveys applicable Workflow Status instructions. These are workflow semantics rather than Direct transport controls. Inclusion of an optional Task does not itself require the receiving endpoint to implement Task interpretation or execution.

| Task concept | Common requirement |
| --- | --- |
| Workflow Activity identification | When present, Task.code SHALL carry the same transaction code and code system as SubmissionSet.purpose. The designated Task.identifier SHALL identify the same logical Workflow Activity as SubmissionSet.uniqueId. |
| Context Instance identifiers | Carries/correlates the Context Instances required by the Transaction Definition. The activity represented by the Task occurs in the context of those established Context Instances; the Task does not create a new Context Instance merely by referencing one. |
| Transaction correlation | Carries the identifiers needed to relate the Workflow Activity to an originating or otherwise related Transaction Instance when the Transaction Definition requires correlation. |
| structured payload acceptance reporting request | Indicates whether structured payload acceptance reporting is requested. Absence of the request does not suppress permitted or required Workflow Status reporting. |
| Workflow Status Update Endpoint | R, 1..* for originating transactions that use TX8 reporting. One or more Direct endpoints designated to receive TX8 Workflow Status for the originating Transaction Instance. |

When a Workflow Activity Task is present, Task.code SHALL carry the same transaction code and code system as SubmissionSet.purpose and apply the TransactionTypesVS Extensible binding in Section 3.7.6. Context Instance type declarations SHALL apply the Extensible binding in Section 3.6.2. Each Transaction Definition identifies its transaction code and any explicit use-case or transaction-specific fixed values. An endpoint supporting an originating transaction MAY process an otherwise conformant package without interpreting or executing an optional Task, unless that Task processing is explicitly required by the applicable Transaction Definition and within the endpoint’s declared capabilities. The presence of an unsupported optional Task SHALL NOT by itself constitute a processing anomaly or rejection reason.

When a Workflow Activity Task is present and TX8 reporting is applicable, workflow status instructions SHALL be carried in that Task rather than Direct transport headers, and the Task SHALL carry the information needed to correlate a subsequent TX8 report with the originating Transaction Instance. When Task is absent and TX8 reporting is required, destination resolution SHALL follow Section 3.9.7; the originating SubmissionSet business identifier SHALL remain available for correlation. Task presence alone does not establish TX8 reporting obligation, and support for an originating transaction does not imply TX8 send or receive support.

An intermediary that adds a Workflow Status Update Endpoint MAY carry an updated representation of the same logical Workflow Activity Task. The updated representation SHALL have a new Task.id while preserving the designated Task.identifier, the requested Shared Activity, existing endpoint instructions, and other transaction information that remains applicable. References and metadata describing the updated Task SHALL resolve to the carried representation; unchanged information objects MAY be retained. The intermediary SHALL add Provenance for its update without modifying another actor’s assertions. This package-representation rule does not prescribe changing a FHIR server resource’s id during an ordinary server-managed update.

No more than one Workflow Activity Task SHALL be carried per workflow unit. TX8 SHALL carry exactly one Workflow Activity Task. TX8's primary information object SHALL be a minimal identification snapshot of the originating SubmissionSet/List being reported on. TX8's own report SubmissionSet/List and Workflow Activity Task are separate objects. A second Workflow Activity Task SHALL NOT be added.
